# ПУЛЬС — интернет-магазин компьютерных комплектующих

Монорепозиторий по ТЗ «На разработку интернет-магазина компьютерных комплектующих».
Реализация идёт по восьми этапам из раздела 21 ТЗ.

**Статус: этап 1 из 8 — фундамент (инфраструктура, каркас backend и frontend).**

## Стек

| Слой | Технологии |
|---|---|
| Frontend | React 19, TypeScript, React Router 7 (**SSR**), Vite 8, Tailwind CSS 4, TanStack Query, Zustand |
| Backend | Python 3.12+, FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), Alembic, PostgreSQL 17, Redis 8 |
| Инфраструктура | Docker Compose, Nginx, GitHub Actions, S3-совместимое хранилище (в dev — файловый том) |

SSR выбран не по вкусу: раздел 11 ТЗ требует индексацию карточек товаров,
`sitemap.xml`, уникальные `title`/`description` и Open Graph — SPA без SSR
закрывает это только костылями.

## Быстрый старт

### Docker (рекомендуется)

```bash
cp .env.example .env      # Windows PowerShell: Copy-Item .env.example .env
make up                   # или: docker compose up -d --build
```

| Адрес | Назначение |
|---|---|
| <http://localhost:8090> | Магазин (через Nginx) |
| <http://localhost:8090/docs> | Swagger UI |
| <http://localhost:3000> | Frontend напрямую (SSR, минуя Nginx) |
| <http://localhost:8010/health> | Backend напрямую |
| <http://localhost:8010/api/v1/health/ready> | Проверка БД и Redis (200 / 503) |

Хостовые порты подобраны так, чтобы не конфликтовать с другими локальными
сервисами: магазин — 8090, backend — 8010, PostgreSQL — 5433, Redis — 6380
(на этой машине 8080, 8000, 5432 и 6379 уже заняты другими стеками).
Меняются в `.env` — внутри контейнеров порты фиксированы.

Миграции применяются автоматически: сервис `migrate` отрабатывает перед стартом `backend`.

### Без Docker

```bash
# Backend
cd backend
uv sync
uv run alembic upgrade head
uv run uvicorn app.main:app --reload

# Frontend (в отдельном терминале)
cd frontend
npm install
npm run dev
```

Нужны свои PostgreSQL, Redis и S3-совместимое хранилище — их адреса берутся
из `backend/.env.example`.

## Ключевые технические решения

1. **Характеристики товаров** хранятся в типизированной паре `attribute_defs` + `product_specs`
   (`value_num` / `value_text` / `value_bool`), а не в текстовом EAV из раздела 7.6 ТЗ.
   Иначе невозможны диапазонные фильтры вроде «TDP 65–125 Вт» или «объём 1–2 ТБ»
   и сортировка по характеристикам. Таблица `product_attributes` из ТЗ остаётся
   источником для отображения и выгрузки.

2. **Деньги** — `NUMERIC(12,2)` и `Decimal`, никакого float. Все итоги, скидки и промокоды
   считает backend (раздел 22 ТЗ: фронтенд не определяет цену и доступность).

3. **Остатки** — через `reserved_quantity` и блокировку строк в транзакции;
   нельзя заказать больше, чем есть, даже при одновременных запросах
   (критерий приёмки №8).

4. **Сессии пользователя** вынесены в отдельную таблицу: без неё refresh-токен
   нельзя отозвать по конкретному устройству, и «выход» убивал бы все сессии разом.

5. **Пароли и токены вычищаются из логов** фильтром `SecretRedactingFilter` —
   раздел 10 ТЗ запрещает их попадание в логи.

6. **В production дефолтные секреты не проходят валидацию** — приложение не стартует
   с `SECRET_KEY=change_me`.

7. **Поиск** строится на `pg_trgm` (устойчив к опечаткам и запросам вида «7800x3d»),
   расширения `unaccent` и `btree_gin` создаются миграцией `0001_foundation`.

## Безопасность

Реализовано в этапе 1:

- CORS только с разрешённых доменов;
- валидация всех входящих данных (Pydantic v2);
- единый формат ошибок `{"error": {"code", "message", "fields"}}`;
- редактирование паролей и токенов в логах;
- отказ от дефолтных секретов в production;
- ограничение частоты запросов на Nginx и `X-Request-ID` для трассировки.

Все маршруты, кроме `/health` и `/api/v1/health`, закрыты по умолчанию —
роли и защита админских маршрутов появятся на этапе 2.

## Оплата в MVP

Платёжный провайдер — фейковый: страница подтверждения лежит внутри магазина,
подпись вебхука настоящая (HMAC-SHA256). Так проверяется весь цикл «заказ →
оплата → статус» без внешней системы. Подключение реального провайдера —
реализация интерфейса `app.payments.PaymentProvider`; сервисы заказов при этом
не меняются.
