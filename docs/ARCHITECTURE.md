# Архитектура ПУЛЬС

Документ описывает принятые решения и отклонения от ТЗ.
Актуальная версия ТЗ: раздел «Техническое задание на разработку
интернет-магазина компьютерных комплектующих».

## 1. Общая схема

```
                    ┌──────────────┐
   Браузер ────────▶│    Nginx     │  :8080
                    │  gzip, лимиты│
                    │  запросов    │
                    └──┬────────┬──┘
             /api/v1/* │        │ /* и /assets
                       ▼        ▼
              ┌────────────┐  ┌──────────────────┐
              │  Backend   │  │ Frontend (SSR)   │
              │  FastAPI   │◀─│ React Router 7   │
              │  :8000     │  │ react-router-    │
              └──┬─────┬───┘  │ serve :3000      │
                 │     │      └──────────────────┘
        ┌────────▼─┐ ┌─▼──────┐        ┌─────────────────────┐
        │PostgreSQL│ │ Redis  │        │ Изображения         │
        │   :5432  │ │ :6379  │        │ local → том /app/media│
        └──────────┘ └────────┘        │ s3    → MinIO/YOS/S3 │
                                       └─────────────────────┘
```

Браузер ходит в API по относительному пути `/api/v1` (его проксирует Nginx),
SSR-сервер — по внутренней docker-сети через `API_INTERNAL_URL`. Благодаря
этому один и тот же код работает в обоих контекстах, а SSR не ходит в себя
по кругу.

### Хранилище изображений

Раздел 2.3 ТЗ рекомендует S3-совместимое хранилище. Реализован интерфейс
`StorageDriver` с двумя реализациями, переключение — одной переменной:

| `STORAGE_DRIVER` | Где лежат файлы | Когда применять |
|---|---|---|
| `local` | том `/app/media`, раздаёт backend с `/media` | разработка, стенд, тесты |
| `s3` | любое S3-совместимое хранилище через boto3 | продакшен |

Причина такого разделения: dev-стек не должен зависеть от внешнего
S3-сервиса, который нужно поднимать, настраивать и обновлять, а код
каталога при этом остаётся одинаковым. Бакет в S3 создаётся автоматически
при первом обращении.

## 2. Решения, отличающиеся от буквы ТЗ

### 2.1. Характеристики товаров: `attribute_defs` + `product_specs`

**ТЗ, раздел 7.6** предлагает `product_attributes (product_id, attribute_name,
attribute_value)` — текстовый EAV.

Проблема: разделы 5.2 и 12 требуют диапазонные фильтры («количество ядер»,
«тепловыделение 65–125 Вт», «объём 1–2 ТБ», «частота 3200–6000»), сортировку
по характеристике и индексы. Над текстовыми значениями это не строится
эффективно и не сравнимо численно.

**Решение.** Две таблицы:

```sql
attribute_defs (
  id, key, name, data_type,      -- text | number | bool | enum
  unit,                           -- "Вт", "ГБ", "МГц"
  filter_widget,                  -- range | checkbox | select | slider
  options,                        -- JSONB со значениями enum
  is_filterable, is_comparable,   -- is_comparable питает сравнение (5.5)
  sort_order
)

product_specs (
  product_id, attribute_id,
  value_num, value_text, value_bool,
  UNIQUE (product_id, attribute_id)
)
```

Индексы: `(attribute_id, value_num)` для диапазонов, GIN по `value_text` для
значений enum, `(product_id)` для выборки характеристик карточки.

Выигрыш: фильтры, сортировка и сравнение работают на индексируемых полях,
набор фильтров добавляется новой строкой в справочнике — без изменения кода
и фронта, и бэка.

Раздел 2.1 перечисляет React и Vite; React Router 7 в framework mode

### 2.5. Платёжный провайдер

Раздел 5.9: «конкретный платежный сервис подключается отдельно через API».
Сделана абстракция `payments.PaymentProvider` с методом
`create_payment` / `verify_webhook`. На MVP — `FakePaymentProvider`:
он проводит оплату и подписывает вебхук тем же секретом, что и бэкенд,
чтобы сценарий целиком проверялся локально. Реальный провайдер добавляется
реализацией интерфейса без изменений в сервисах заказов.

### 2.6. Фоновые задачи

Раздел 2.3 допускает Celery или BackgroundTasks. На MVP — BackgroundTasks:
письма, резервы и импорт не требуют брокера. Когда появится расписание
(TTL резервов, отчёты) — переезд на Celery поверх того же Redis.

## 3a. Каталог: как устроены фильтры

Фильтры раздела 5.2 ТЗ не зашиты в код. Каждая строка в `attribute_defs`
описывает один фильтр: ключ (`cpu.tdp`), название, тип значения, единицу
измерения, виджет и — для enum — список значений.

Запрос к бэкенду выглядит одинаково для любой характеристики:

```
/api/v1/products?category=processory&attr.cpu.socket=AM5&attr.cpu.tdp.min=100&attr.cpu.tdp.max=130
```

Фронтенд строит панель фильтров целиком по `facets.attributes` — добавить
новый фильтр можно, вставив строку в справочник, без правок на обеих сторонах.

### Почему `product_specs`, а не `product_attributes`

Текстовый EAV из раздела 7.6 ТЗ не позволяет построить диапазонный фильтр
(«TDP 100–130 Вт»), сортировку по характеристике и индекс по значению.
В `product_specs` значения типизированы: числа лежат в `value_num`, перечисления
и текст — в `value_text`, булевы — в `value_bool`. Индексы
`(attribute_id, value_num)` и `(attribute_id, value_text)` покрывают оба случая.

### Фасеты считаются без собственного фильтра

Счётчик рядом с фильтром показывает, сколько товаров будет, если его включить,
поэтому считается он по выборке **без** самого фильтра. Иначе выбор галочки
обнулял бы её же счётчик, и фильтр нельзя было бы снять.

### Доступный остаток считается, а не хранится

Колонки `available` в таблице нет: `stock_quantity - reserved_quantity`
вычисляется в SQL. Хранить производное значение опасно — оно расходится с
исходными данными при любом параллельном изменении остатка.

### Статус в интерфейсе отличается от статуса в базе

Товар со статусом `in_stock` и остатком 2 показывается как «мало на складе».
Состояние выводится из фактического остатка (`effective_status`), а в базе
остаётся значение, заданное администратором, — иначе любое чтение каталога
переписывало бы редакторские данные.

### Сортировка всегда стабильна

Во всех шести вариантах сортировки последним условием идёт `id`. Без него две
строки с одинаковым значением сортировки могли бы «прыгать» между страницами,
и покупатель увидел бы дубли и пропуски.

## 3. Статусы заказа

11 статусов раздела 5.10 оформлены явной матрицей переходов, а не цепочкой
условий. Каждая смена статуса:

1. проверяется по матрице (недопустимый переход — 409);
2. пишется в `admin_audit_log`;
3. порождает уведомление пользователю;
4. при переходе в «Оплачен» списывает резерв в `stock_quantity`,
   при отмене — возвращает.

Пользователю доступна отмена только до статуса «Собирается».

## 3b. Заказы: резервы, статусы, оплата

### Резерв отличается от списания

```
оформление  → reserved_quantity += N   (stock не меняется)
оплата      → reserved -= N, stock -= N
отмена      → reserved -= N           (stock не менялся)
```

Резерв уменьшает **свободный** остаток (`stock - reserved`), но не сам
`stock_quantity`. Товар остаётся на складе до оплаты и уходит из продажи
раньше, чем физически отгружен. Обе операции выполняются под
`SELECT ... FOR UPDATE OF products`: без блокировки два одновременных заказа
могли бы суммарно превысить остаток (критерий приёмки №8).

Блокировку приходится ограничивать именно таблицей товара: у `Product` есть
`lazy="joined"` связи, они присоединяются через LEFT JOIN, а PostgreSQL
запрещает `FOR UPDATE` на nullable-стороне внешнего соединения.

### Статусы описаны таблицей переходов

Одиннадцать статусов раздела 5.10 и 21 переход описаны в `TRANSITIONS`.
Каждый переход объявляет побочный эффект: `hold` (ничего), `release`
(вернуть резерв), `capture` (списать), `return` (вернуть товар на склад).
Переход вне таблицы — 409 `invalid_status_transition` со списком
разрешённых статусов, а не 500.

Побочные эффекты нельзя вынести из таблицы: списание остатка, возврат
брони и уведомление должны случиться ровно в момент смены статуса, иначе
заказ «оплачен, но товар не списан» или «отменён, а товар зарезервирован».

### Цены не из клиента

`OrderCreate` не содержит цен и сумм. Клиент присылает состав корзины и
данные покупателя; всё считает `services.pricing`. Позиции заказа хранят
копию названия, артикула и цены — правка карточки товара не меняет
оформленные заказы (критерий №25).

### Идемпотентность оформления

Заголовок `Idempotency-Key` сохраняется в `orders.idempotency_key` с
уникальным индексом. Повторный POST с тем же ключом возвращает уже
созданный заказ: двойной клик по кнопке или перезагрузка страницы не
приводят к двум заказам (раздел 10 ТЗ).

### Оплата

`PaymentProvider` — интерфейс с тремя методами. В MVP работает
`FakePaymentProvider`: он выдаёт идентификатор платежа, подписывает токен
страницы оплаты HMAC-SHA256 и **требует подписи на вебхуке**. Без проверки
подписи любой желающий отметил бы заказ оплаченным, поэтому подделка вебхука
отклоняется с 400.

Разделитель полей токена — «~», а не «.»: сумма вида «36560.00» содержит
точку, и разбор по точкам разваливал токен.

### Просроченные резервы

Заказ, не оплаченный за `reservation_ttl_hours` (48 по умолчанию),
теряет бронь: `app.cli release-reservations` (планировщик — раз в час).
Без этого резерв блокировал бы товар навсегда.

## 3c. Админ-панель

### Права проверяются на маршруте, а не в интерфейсе

Два роутера с разными требованиями: `staff_router` (менеджер и выше) и
`admin_router` (только администратор). Менеджер, попавший на каталог или
пользователей, получает 403, а не пустой список: иначе интерфейс выглядел
бы как «данных нет», а на самом деле их смотреть нельзя.

### Журнал действий пишется в той же транзакции

`AuditService.record()` добавляет запись в ту же сессию, что и изменение.
Отдельный коммит означил бы, что действие могло откатиться, а запись в
журнале — остаться. Пароли в журнал не попадают: фиксируется сам факт
сброса, значение заменяется на «***».

### Специальные защиты от «уронить магазин»

- администратор не может заблокировать самого себя — иначе единственный
  сотрудник с доступом теряет панель;
- нельзя заблокировать последнего активного администратора;
- категория не может быть вложена глубже второго уровня (раздел 6.2);
- товар, который уже есть в заказах, удалить нельзя — только скрыть
  (иначе позиции истории потеряли бы название);
- списание больше, чем на складе, отклоняется — остаток не уходит в минус;
- старая цена не может быть ниже текущей — иначе скидка отрицательная.

### Импорт: сначала отчёт, потом данные

`POST /admin/products/import` по умолчанию работает в режиме `dry_run`:
разбирает файл, сверяет артикулы со справочниками категорий и брендов и
возвращает отчёт — что создастся, что пропустится и в какой строке какая
ошибка. Реальная загрузка — отдельный вызов с `dry_run=false`.

Сообщения об ошибках называют колонку и строку: сотрудник открывает файл и
видит проблему, а не гадает, почему товар не загрузился.

## 4. Работа с остатками

```
available = stock_quantity - reserved_quantity
```

Резерв создаётся в одной транзакции с заказом и `SELECT … FOR UPDATE`
на строках товаров — конкурентные заказы не могут суммарно превысить остаток
(критерий приёмки №8). Резерв имеет TTL: просроченные брони фоновой задачей
возвращаются в свободный остаток.

## 5. Логи

Раздел 13 требует пять уровней и запрет утечки секретов.
Фильтр `SecretRedactingFilter` вычищает значения по списку чувствительных
ключей на любом уровне вложенности (`password`, `*_token`, `secret`, `api_key`,
`card_number`, `cvv`, `smtp_password`) и маскирует заголовки `Bearer`/`Basic`.
В production формат записи — JSON, в разработке — человекочитаемый.

Каждый ответ API несёт `X-Request-ID`, который дублируется в логах backend и
nginx — это позволяет связать обращение пользователя с конкретной ошибкой.
